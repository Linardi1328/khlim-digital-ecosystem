## Media contract

The [current rights inventory](../../media/RIGHTS-MANIFEST.md#2026-11-25-v1-release-classification) covers all 54 baseline files under Web and Admin `public/`. The web build contains 35 fewer files, including all 32 youth or potentially youth-identifying photos. All previously approved adult coach portraits, official Academy, Club and KHLIM logos, and three KHero posters remain. The two KHS partner-mark copies are scoped to confirmed partnership surfaces and had no current use. An unapproved, unused KHero placeholder was also removed.

- Home uses the existing branded gradient hero as a single panel with its heading and links. Academy uses the existing crest and training fallback. Neither requests the retired hero or training images.
- Spotlight and Home retain fact-verified achievement and representative copy and neutral gallery frames. Public editorial list and detail endpoints return `imageUrl: null`. Their staff equivalents retain existing behavior. The web adapter drops URLs outside the exact youth-media approval list, which is empty for V1. Legacy flag values and editorial booleans cannot add to that list.
- Removed URLs return 404 on a fresh production build. Image optimizer requests for the same sources also fail. The existing internal preview page returns 404 in production and its file endpoint returns 403. Keep the local review pack outside the build and use the development preview on a loopback-only server.
- Use existing private club records for any original photos and consent evidence KHLIM has a basis to retain. There is no V1 need to serve those photos over HTTP. If an authorized private review workflow later needs hosted delivery, require access control and current asset-specific rights at origin, prevent shared caching, and make revocation effective within the permitted access window. Keep the consent records private. A registration photography opt-in does not establish public-use permission for historical photos or derivatives.

## API boundary

Only the exact value `1` in the corresponding **API runtime** environment variable enables a guarded customer route. Missing, blank, malformed and all other values fail closed. The launch gate runs after existing authentication and authorization and before customer services perform writes or call a payment provider. The closed response is HTTP 403 with `code: "CUSTOMER_FEATURE_DISABLED"`. Auth failures retain their existing responses.

| API under `/v1` | V1 release behavior |
| --- | --- |
| `POST /athletes/:athleteId/memberships` | Requires `KHLIM_ENABLE_V1_PAID_ENROLMENT=1` and existing manage access. This route creates a pending customer purchase under the actor's identity. |
| `POST /athletes/:athleteId/memberships/:membershipId/checkout` | Same launch and manage checks, followed by existing purchaser, pending status, terms, capacity and Billplz configuration checks. Customer initiation has one provider entry point. |
| `POST /me/athletes`, `POST /me/athletes/:athleteId/guardian-invitations`, `POST /family-invitations/accept` | Requires `KHLIM_ENABLE_V1_PARENT_PORTAL=1` in addition to each route's existing authentication, role or athlete-access policy. These routes create athlete records or grant new family access. |
| `GET /me/schedule`, `GET /me/notifications`, `POST /me/notifications/:id/read` | Already fail closed. The global `AuthorizationGuard` rejects them for missing authorization metadata. Any future launch of these routes requires explicit authorization policies and a portal launch check. |
| `GET /academy/offerings`, Register Interest and account/profile/preferences routes | Existing behavior. The account and guardian-profile operations support account registration and sign-in. |
| Existing athlete reads and edits, family-link or invitation revocation, membership reads and billing history | Existing access policies. Customers with the required permissions can manage existing records, revoke access and review payment history. |
| Staff operations and `POST /admin/billing/reconcile-stale-checkouts` | Existing staff, organization and MFA policies. This preserves staff programme/plan configuration, membership/payment records and reconciliation. |
| `POST /payments/webhooks/:provider` | Existing signature/raw-body verification, organization checks and idempotent settlement. Provider callbacks for existing charges must continue to work with checkout closed. |
| `GET /academy/registration-config`, `GET /academy/sessions`, `POST /academy/registrations`, and Academy Registration admin routes | Existing [RIC-190/RIC-191 contract](ric-191-academy-registration-handoff.md). Registration requires its own policy, HMAC and session prerequisites. The receipt is non-reserving and has no checkout. |

`NEXT_PUBLIC_ENABLE_V1_ENROLMENT` and `NEXT_PUBLIC_ENABLE_V1_PORTAL` are presentation settings in RIC-184. A later approved paid enrolment launch that includes adding a player will also need the portal creation capability. The frozen registration migrations, hosted config, payment settings and registration release state are outside this diff.

## Remaining hosted work — owner authorization required

1. Have the safeguarding owner open or update the takedown record in the club's private system. Record the request, exact source/derivative URLs, evidence references, owner, timing and outcome. Suspend public distribution pending the per-asset decision. Collect photographer/licence and guardian public-use evidence for assets considered for re-release. Keep personal details out of public issues and logs.
2. Inventory live and staging aliases, immutable preview URLs, previous builds, mirrors and original sources. Start from the Web release in [PR #103](https://github.com/Linardi1328/khlim-digital-ecosystem/pull/103) and previews or artifacts built from its descendants or earlier photo branches. Check any CI walkthrough exports, screenshots, PR assets and externally hosted editorial URLs. Prior branch refs can retain duplicate copies in Web or Admin. Use production, staging and preview inventories as evidence of scope.
3. After separate release approval, replace affected live builds with the sanitized version and retire or restrict older affected deployment URLs. Purge raw CDN URLs and all image transforms, including `/_next/image` variants and any downstream caches. A purge can refill from an old accessible build. Vercel image caches can persist across deploys. [Vercel deployments](https://vercel.com/docs/deployments/managing-deployments) · [Vercel image cache](https://vercel.com/docs/image-optimization)
4. Verify unauthenticated raw URLs, optimized variants and public editorial responses on every affected alias and immutable URL from a clean client. Record status, content type and cache behavior without downloading or redistributing photos. Escalate any surviving origin, artifact or cache. Browser caches, saved files and third-party copies require their own follow-up.
5. Assess Git history, historical PR refs and cached views with the repository owner. Coordinate any needed rewrite or redaction separately and work with GitHub Support, collaborators and fork owners where applicable. This PR removes files from the new tree and leaves historical objects reachable. [GitHub sensitive-data removal](https://docs.github.com/en/authentication/keeping-your-account-and-data-secure/removing-sensitive-data-from-a-repository)
6. Verify hosted API gate variables are absent or disabled for V1 on every serving API deployment. Smoke-test with an authorized synthetic guardian, finance staff and signed sandbox test fixtures only in an approved environment. Avoid routing customers to an older API that still permits initiation.
